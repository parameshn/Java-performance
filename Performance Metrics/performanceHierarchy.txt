This section is one of the most valuable in the introduction. The author's main message is:
	The JVM is only one part of application performance. Good algorithms, clean code, proper architecture, and correct bottleneck analysis matter just as much—often more.
Let's go through each idea with practical scenarios.

1. Write Better Algorithms
The author says:
	There is no -XX:+RunReallyFast JVM flag. A better algorithm beats JVM tuning.
Scenario
You need to search for a customer.
Version A
for(Customer c : customers){
    if(c.getId()==id)
        return c;
}
Complexity:
O(n)
If there are:
1,000,000 customers
you may examine nearly all of them.

Version B
HashMap<Integer, Customer> customers;
Lookup:
customers.get(id);
Complexity:
O(1)
Even if you tune the JVM perfectly, the first algorithm won't outperform the second. Algorithm choice dominates performance.

2. Write Less Code
The author introduces the idea of "death by 1,000 cuts."
Scenario
Version 1:
Inventory Service
20 classes
Version 5 (after many small features):
Inventory Service
250 classes
Each developer says:
	"I'm only adding one tiny feature."
But over time:
	• more classes to load,
	• more objects to allocate,
	• more methods for the JIT to compile,
	• more garbage to collect.
No single change hurts much, but hundreds of small additions gradually slow the application.

3. Software Gets Slower Over Time
The author points out that software naturally accumulates features and complexity.
Scenario
Browser version 1:
Open web page
Browser version 20:
Open page
Extensions
Sync
Security
Password Manager
Developer Tools
AI Assistant
It offers much more functionality, but also does more work.
This is why performance engineering is an ongoing process.

4. Premature Optimization
The famous quote is often misunderstood.
The author's point:
	Don't write complicated code for tiny gains, but don't ignore obvious inefficiencies either.
Bad Example
log.info("Price = " + calculatePrice());
Even when INFO logging is disabled:
	• calculatePrice() still runs.
	• The string is still built.

Better
if (log.isLoggable(Level.INFO)) {
    log.info("Price = " + calculatePrice());
}
Now expensive work only happens when needed.

5. The Database Is Usually the Bottleneck
This is one of the book's most memorable observations.
Scenario
Imagine a Spring Boot application.
Client
   │
   ▼
Spring Boot
   │
   ▼
PostgreSQL
Suppose:
Spring Boot processing
5 ms
Database query
450 ms
Total:
455 ms
Now you optimize Java code.
Java
5 ms
↓

2 ms
Total becomes:
452 ms
The user barely notices the difference because the database dominates the response time.

6. Bugs Aren't Always in Java
The author shares a real story where the problem wasn't the application server—it was the load-testing tool (JMeter).
Scenario
Your API becomes slow after deployment.
Possible suspects:
Spring Boot
Database
Network
Docker
Nginx
Redis
Load Balancer
Testing Tool
Don't assume:
	"Java is slow."
Measure first.

7. Optimizing the Wrong Component Can Hurt
This is a subtle but important point.
Scenario
Database capacity:
1000 queries/sec
Java server currently sends:
900 queries/sec
Everything works.
Now you optimize Java and it sends:
1500 queries/sec
The database becomes overloaded.
Instead of improving performance:
Database queue grows
↓

Response time increases
↓

Entire system becomes slower
Making one component faster isn't always beneficial if another component is already saturated.

8. Optimize the Common Case
The author advises focusing on the operations users perform most often.
Scenario
An e-commerce site:
95%
Search Products
View Products
Add to Cart
Checkout
5%
Generate Annual Sales Report
If you spend two weeks optimizing the annual report while product searches remain slow, users won't notice.
A better investment is optimizing the search path because that's where most requests occur.

Overall Lesson
The chapter can be summarized with this hierarchy:
Performance
│
├── Good Algorithms        ⭐⭐⭐⭐⭐
├── Simple Design          ⭐⭐⭐⭐
├── Database Efficiency    ⭐⭐⭐⭐
├── Correct Architecture   ⭐⭐⭐⭐
├── Profiling & Measurement⭐⭐⭐⭐
├── JVM Ergonomics         ⭐⭐⭐
├── GC Tuning              ⭐⭐
└── JVM Flags              ⭐
The book doesn't say JVM tuning is unimportant. Rather, it emphasizes that JVM tuning should come after you've chosen good algorithms, written clean code, and identified the actual bottleneck. Those foundations usually have a much larger impact on performance than tweaking JVM flags alone.
